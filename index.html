Plan de calidad, pruebas y despliegue del sistema SIGEC

Continuación del proyecto de análisis de requerimientos de TechSolutions: se define el modelo de calidad, las métricas, el plan de pruebas, la gestión de la configuración, el despliegue y el soporte post-entrega del sistema de gestión de inventario de equipos de cómputo.

Contexto del proyecto

TechSolutions es una organización de aproximadamente 1000 empleados cuyo control de equipos de cómputo se realizaba de forma manual en archivos de Excel independientes, generando duplicidad de información, ausencia de alertas de obsolescencia y falta de reportes confiables para el presupuesto de renovación tecnológica. A partir de ese diagnóstico se definieron 8 requerimientos funcionales (RF-01 a RF-08) y 8 no funcionales (RNF-01 a RNF-08) para SIGEC, el sistema que centraliza y automatiza esa gestión.

Esta actividad retoma SIGEC para diseñar su plan de calidad y pruebas, y complementarlo con la planeación del despliegue, la gestión de la configuración, el soporte y la documentación posteriores a la entrega.

Requerimiento Funcionales

RF-01: El sistema debe permitir registrar cada equipo de cómputo con sus atributos: marca, modelo, número de serie, fecha de compra, área asignada y usuario responsable

RF-02: El sistema debe permitir clasificar el estado de cada equipo en activo, en proceso de renovación u obsoleto

RF-03: El sistema debe generar alertas automáticas cuando un equipo supere el tiempo de vida útil definido por la organización

RF-04: El sistema debe permitir la búsqueda y filtrado de equipos por área, usuario, marca o estado

RF-05: El sistema debe permitir generar reportes exportables en PDF y Excel del inventario tecnológico

RF-06: El sistema debe registrar el historial de mantenimiento y cambios de estado de cada equipo

RF-07: El sistema debe permitir la asignación y reasignación de equipos a los empleados

RF-08: El sistema debe contar con perfiles de acceso diferenciados (administrador, técnico y consulta)

Requerimientos No Funcionales

RNF-01: Usabilidad, la interfaz debe ser intuitiva y de fácil manejo para personal técnico sin capacitación avanzada

RNF-02: Disponibilidad, el sistema debe estar disponibilidad al menos el 99% del tiempo en horario laboral

RNF-03: Seguridad, el acceso debe requerir autenticación y los datos deben almacenarse cifrados

RNF-04: Escalabilidad, el sistema debe soportar el crecimiento del inventario hasta 1500 equipos sin degradar el rendimiento

RNF-05: Rendimiento, las consultas y búsquedas deben responder en un tiempo menor a 3 segundos

RNF-06: Compatibilidad, el sistema debe integrarse con el DA corporativo

RNF-07: Mantenibilidad, el código debe estar documentado para permitir su actualización por el equipo de TI interno

RNF-08: Cumplimiento normativo, el manejo de datos personales de los usuarios debe cumplir con la normativa de protección de datos vigentes

Paso 01

Normas y modelos de calidad

Modelo seleccionado: ISO/IEC 25010:2011

Se adopta el modelo de calidad de producto de software ISO/IEC 25010 como marco principal, complementado con ISO/IEC/IEC 29119 para el proceso de pruebas. La elección responde a tres razones concretas para SIGEC:

  1. Continuidad con el análisis previo. los ocho requisitos no funcionales definidos presentan una correspondencia directa con las características de calidad contempladas en el modelo ISO/IEC 25010. Por tanto, se mantiene este estándar como marco de referencia para evaluar la calidad del sistema, garantizando coherencia con el análisis realizado previamente y evitando reinterpretar los criterios de calidad desde cero.
  2. Cobertura de producto, no solo de proceso. A diferencia de CMMI (que evalúa la madurez del proceso de desarrollo), ISO/IEC 25010 evalúa directamente el software resultante, que es lo que la jefatura de TI y los técnicos de soporte perciben y usan a diario.
  3. Aplicabilidad a un equipo pequeño. El equipo de TI interno que dará mantenimiento a SIGEC es reducido; un modelo de producto con 8 características verificables es más viable de aplicar y auditar que un marco de madurez organizacional como CMMI, que exige una estructura de procesos más amplia.

De forma complementaria, se toma como referencia de proceso un enfoque ágil con revisiones de calidad por iteración (inspirado en prácticas de CMMI nivel 2-3: gestión de requerimientos y aseguramiento de calidad), sin adoptar la certificación completa.

Paso 02

Métricas de calidad

Cinco métricas aplicables a SIGEC, cada una ligada a un requerimiento no funcional y a una forma concreta de medición.

Tiempo de respuesta < 3 s

Cómo se mide: herramienta de monitoreo (APM) que registra el percentil 95 (p95) de latencia del endpoint de búsqueda y filtrado, muestreado en horario laboral. Vinculada a RNF-05.

Disponibilidad del sistema ≥ 99 %

Cómo se mide: (horas operativas − horas de caída) / horas operativas × 100, calculado mensualmente con un monitor de uptime sobre el horario laboral. Vinculada a RNF-02.

Densidad de defectos < 5 críticos / release

Cómo se mide: conteo de defectos por severidad registrados en el gestor de incidencias (Jira) durante QA, dividido entre los módulos entregados en cada versión.

Cobertura de pruebas ≥ 80 %

Cómo se mide: porcentaje de líneas y ramas ejecutadas por pruebas automatizadas, calculado por una herramienta de cobertura integrada al pipeline de integración continua.

Usabilidad percibida (SUS) ≥ 70 / 100

Cómo se mide: cuestionario System Usability Scale de 10 preguntas aplicado a técnicos y usuarios finales tras la capacitación piloto. Vinculada a RNF-01.

Paso 03

Plan de pruebas

Casos de prueba
IDCaso de pruebaResultado esperadoTipo
TC-01 Registrar un equipo nuevo con marca, modelo, número de serie, fecha de compra, área y usuario responsable. El equipo queda almacenado y visible en el listado general con estado "Activo". Funcional
TC-02 Cambiar manualmente el estado de un equipo a "Obsoleto" desde el panel de gestión. El nuevo estado se refleja de inmediato en el listado y en los reportes generados. Funcional
TC-03 Registrar un equipo cuya fecha de compra supere la vida útil definida por la organización (ej. 4 años). El sistema genera una alerta automática visible para la jefatura de TI, sin intervención manual. Integración
TC-04 Filtrar el inventario por área "Contabilidad" y estado "Activo". Los resultados mostrados corresponden exactamente a los criterios filtrados, sin registros ajenos. Funcional
TC-05 Generar un reporte del inventario completo en formato PDF y en Excel. Ambos archivos se descargan correctamente y contienen la totalidad de los registros vigentes, sin truncamientos. Funcional
TC-06 Iniciar sesión con un perfil de "Consulta" e intentar editar un registro existente. El sistema deniega la acción y muestra un mensaje de permisos insuficientes. Seguridad
TC-07 Simular un inventario de 1500 equipos con 50 usuarios concurrentes ejecutando búsquedas. El tiempo de respuesta se mantiene por debajo de 3 segundos y el sistema no presenta caídas. Carga

Criterios de aceptación del software

  • El 100 % de los casos de prueba funcionales críticos (TC-01 a TC-05) debe pasar sin defectos bloqueantes.
  • No se acepta ningún defecto crítico o alto sin resolver al momento de la entrega; se admite un máximo de defectos menores documentados en el backlog.
  • El tiempo de respuesta bajo la carga máxima simulada (TC-07) no debe superar los 3 segundos definidos en RNF-05.
  • El control de acceso por rol (TC-06) debe bloquear el 100 % de los intentos de acción no autorizada durante las pruebas de seguridad.
  • La disponibilidad demostrada durante el piloto (mínimo dos semanas en el entorno de pruebas) debe ser igual o superior al 99 % definido en RNF-02.
Paso 04

Gestión de la configuración

Versionamiento

Se adopta versionamiento semántico sobre un repositorio Git (GitHub/GitLab), con una estrategia de ramas: main refleja siempre lo desplegado en producción, develop integra los avances en curso, y las ramas feature/*, release/* y hotfix/* aíslan el desarrollo de nuevas funciones, la preparación de versiones y las correcciones urgentes respectivamente. Cada versión liberada se marca con una etiqueta (tag) y queda documentada en el changelog.

Desarrollo
Entorno local o compartido del equipo, con datos ficticios. Aquí se integran las ramas feature/* antes de fusionarse con develop.
Pruebas / QA (staging)
Réplica de producción con datos anonimizados. Se ejecutan aquí las pruebas de integración, aceptación (UAT) y de carga antes de aprobar un release.
Producción
Entorno con datos reales de TechSolutions, acceso restringido y monitoreo activo. Solo recibe versiones aprobadas desde main.

Control de cambios

  • Toda solicitud de cambio se registra como ticket en el gestor de incidencias (Jira o Azure Boards), con severidad y responsable asignados.
  • Los cambios se integran mediante pull requests, con al menos un revisor distinto al autor antes de fusionar a develop.
  • Un pipeline de integración continua (CI/CD) ejecuta automáticamente las pruebas unitarias y de cobertura en cada pull request; solo se permite el paso a main si el pipeline es exitoso.
  • Un pequeño Comité de Control de Cambios (jefatura de TI + líder técnico) aprueba formalmente el paso de una release a producción.

Paso 06

Soporte y seguimiento post-proyecto

Estrategia de atención de incidencias y ciclo de mejora continua tras la entrega de SIGEC.

Se establece una mesa de ayuda de TI como único canal de reporte, con un formulario de incidencias dentro del propio sistema (o herramienta de gestión de tickets como Jira Service Management), y tres niveles de atención escalonados.

Niveles de atención y tiempos de respuesta (SLA)
NivelResponsableAlcanceTiempo de respuesta
N1Mesa de ayudaDudas de uso, restablecimiento de acceso< 4 h (crítico)
N2Soporte técnico especializadoFallas funcionales, errores de datos< 24 h (media)
N3Equipo de desarrolloDefectos de código, cambios estructurales< 72 h (baja)

Ciclo de mantenimiento

  • Correctivo: corrección priorizada por severidad de los defectos detectados en producción, gestionados como tickets en el backlog técnico.
  • Evolutivo: ciclos trimestrales de mejora a partir de encuestas de satisfacción y solicitudes de la jefatura de TI, priorizados en conjunto con el área de compras cuando implican nuevo hardware.
  • Seguimiento de indicadores: reuniones mensuales durante los primeros seis meses para revisar las métricas de calidad definidas en el Paso 2 (disponibilidad, tiempo de respuesta, densidad de defectos) y ajustar el plan de mantenimiento.
